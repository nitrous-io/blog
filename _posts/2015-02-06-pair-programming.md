[Pair Programming](http://en.wikipedia.org/wiki/Pair_programming), an element of [Extreme Programming](http://en.wikipedia.org/wiki/Extreme_programming), remains a controversial [Agile Development](http://en.wikipedia.org/wiki/Agile_software_development) practice that developers tend to love or loathe. Experiences vary drastically upon the various combinations of developer proficiency, personality and habits. For the uninitiated, pair programming can be described as something akin to ‘code review on steroids’, but the overarching theme is that an extra pair of eyes ensures improved software quality and fewer defects.

Pair programming isn't all pixie dust and fairy tales however. The additional set of eyes comes with an opportunity cost since developers spend on average [15% more time](http://collaboration.csc.ncsu.edu/laurie/Papers/XPSardinia.PDF) during the initial development phase. This additional time sink is likely due to differences in developer proficiencies and general working styles.

##Incredible benefits, when done right

Although pair programming might not be a panacea for every team, the rewards are tremendous once you’ve found the right programming partner. The benefits of pair programming are numerous: A clean, well designed code base that facilitates maintainability, improved developer awareness of the code base, less time fixing bugs, as well as improved learning & communication. San Francisco’s [Pivotal Labs](http://www.pivotallabs.com) and Toronto’s [Xtreme Labs](http://www.xtremelabs.com) are successful examples of companies who have adopted and benefited from the pair programming methodology.
